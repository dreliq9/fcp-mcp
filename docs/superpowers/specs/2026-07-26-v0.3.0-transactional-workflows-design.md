# fcp-mcp v0.3.0 Transactional Workflows Design

**Date:** 2026-07-26
**Status:** Conversational design approved; written-spec review pending
**Research:** [`docs/research/2026-07-26-phase-1-transactional-workflows.md`](../../research/2026-07-26-phase-1-transactional-workflows.md)

## Context

Version 0.2.1 established a bounded execution plane: allowed-root path policy,
safe automation argument passing, coded failures, verified external commands,
and validated atomic FCPXML writes with backup and rollback.

Version 0.3.0 turns those seams into a deterministic workflow:

```text
inspect -> plan -> dry-run -> validate -> diff -> approve -> commit
```

The purpose is not to make `fcp-mcp` an autonomous agent. The purpose is to let
an outer agent propose structured edits while code owns control flow,
evaluation, approval, persistence, and recovery.

## Approved product decisions

1. Use a bounded transactional state machine, not an SDK beta-first migration
   and not a generic graph framework.
2. Require CLI approval by default. Client-mediated approval is available only
   through explicit startup configuration.
3. Make the `workflow` capability profile the no-argument default.
4. Preserve all existing public tools behind broader profiles.
5. Preserve existing successful text content while adding meaningful typed
   structured content.
6. Develop the SDK-independent workflow core on stable MCP v1, then migrate the
   isolated MCP boundary only after stable v2 and the final specification ship.

## Goals

- Make multi-operation FCPXML edits previewable before destination mutation.
- Bind approval to the exact plan, candidate, diff, and file preconditions.
- Persist every important transition and artifact hash.
- Recover truthfully from interruption at every filesystem/database boundary.
- Expose a small default tool catalog with an explicit path back to all tools.
- Give host applications validated, domain-specific result schemas.
- Keep existing text-channel behavior and public tool inputs compatible where
  safety permits.
- Verify both the workflow trajectory and the final filesystem outcome.

## Non-goals

- A generic user-defined graph engine.
- An LLM loop inside the MCP server.
- MCP Tasks integration in the initial release.
- Background or distributed workers.
- Knowledge graphs, vector memory, RAG, model routing, or multi-agent control.
- Live Final Cut Pro, Compressor, or media-processing actions inside this graph.
- Template placeholder replacement without a separate clip-identity design.
- Removing any existing tool.
- Publishing, tagging, or pushing without separate authorization.

## Architecture

```text
MCP host
   |
   | fcpxml_workflow_prepare(typed plan)
   v
+---------------- deterministic workflow core ----------------+
| inspect -> normalize -> apply in memory -> serialize         |
|        -> validate -> semantic diff -> persist preview       |
+--------------------------------------------------------------+
   |
   v
awaiting_approval
   |
   +---- fcp-mcp workflow reject RUN_ID
   |
   +---- fcp-mcp workflow approve RUN_ID
                  |
                  v
              approved
                  |
                  | fcpxml_workflow_commit(RUN_ID)
                  v
       destination lock -> recheck -> commit intent
               -> atomic replace -> reopen/validate/hash
               -> durable receipt
```

The model controls only the typed operation list. It cannot:

- add or remove graph nodes;
- invoke arbitrary tools inside a run;
- skip dry-run, validation, diff, or precondition checks;
- select the approval mode;
- modify ledger state directly;
- choose artifact or lock paths;
- make a stale approval valid.

## Module boundaries

The implementation plan should preserve these ownership boundaries:

```text
src/fcp_mcp/
├── mcp_boundary.py        # SDK-specific result and registration helpers
├── profiles.py            # static catalog/profile policy
└── workflow/
    ├── models.py          # plans, operations, previews, receipts, states
    ├── operations.py      # closed registry and in-memory application
    ├── engine.py          # fixed graph and transition orchestration
    ├── ledger.py          # SQLite schema, transactions, event history
    ├── artifacts.py       # private candidate/diff storage and hashing
    ├── approval.py        # CLI/client approval binding
    ├── locking.py         # destination-scoped commit locks
    └── recovery.py        # reconciliation and integrity verification
```

The workflow package must not import MCP SDK types. `server.py` and
`mcp_boundary.py` adapt domain inputs/results to the current SDK.

## Capability profiles

Profiles are fixed, documented compositions. They are selected at process
startup and cannot change during a session.

| Profile | Existing tools | Workflow tools | Total | Purpose |
| --- | ---: | ---: | ---: | --- |
| `inspect` | 30 | 0 | 30 | Diagnostics and offline reads |
| `workflow` | 30 | 4 | 34 | Approved transactional editing; default |
| `edit` | 70 | 4 | 74 | All offline reads/writes plus workflows |
| `full` | 89 | 4 | 93 | Complete legacy catalog plus workflows |

The 30-tool inspection set is the current diagnostic plus offline-read
annotation group. The additional 40 offline tools are current offline mutators
and stateful generators. The final 19 tools are current live/open-world tools.

Selection precedence:

1. `fcp-mcp serve --profile PROFILE`;
2. `FCP_MCP_PROFILE`;
3. default `workflow`.

`FCP_MCP_ENABLE_LIVE_CONTROL=1` remains an independent execution gate. Selecting
`full` makes live tools discoverable but does not enable them.

### Prompt routing

A prompt is registered only when every tool call it emits is available.

| Profile | Prompts |
| --- | --- |
| `inspect` | `qc-check`, `youtube-chapters` |
| `workflow` | `qc-check`, workflow-backed `cleanup`, `youtube-chapters` |
| `edit` | all five prompts |
| `full` | all five prompts |

The `cleanup` prompt is rewritten to prepare one transaction containing
`fix_flash_frames` and `fill_gaps`. `rough-cut` and `beat-sync` remain outside
the initial workflow operation registry and therefore require `edit` or `full`.

Every prompt/tool dependency is checked against the active runtime catalog.

## Public workflow surface

### `fcpxml_workflow_prepare`

Annotation: mutating but non-destructive, closed-world.

The call writes only private ledger and preview artifacts. It does not alter the
requested destination.

Input:

```text
schema_version: "1"
source_path: absolute or policy-resolvable FCPXML path
destination_path: absolute or policy-resolvable FCPXML path
operations: 1..100 typed operations
expected_source_sha256: optional caller precondition
idempotency_key: optional caller key, maximum 128 characters
```

Output: `WorkflowPreviewV1`.

### `fcpxml_workflow_status`

Annotation: read-only, non-destructive, closed-world.

Input: `run_id`.

Output: the current state projection, approval state, hashes, warnings, error,
resource URIs, and a read-only reconciliation assessment for interrupted
commits. It never returns full candidate XML and never changes ledger state.

### `fcpxml_workflow_commit`

Annotation: mutating, destructive, non-idempotent hint, closed-world.

Input: `run_id`.

In CLI mode the run must already hold a valid CLI approval. In client mode the
call creates and consumes a client-approval record before committing.

The operation is logically idempotent despite its conservative annotation:
calling it again for a committed run returns the existing receipt only if the
destination still matches the committed output hash.

Output: `WorkflowCommitReceiptV1`.

### `fcpxml_workflow_cancel`

Annotation: mutating, non-destructive, closed-world.

Input: `run_id` and an optional bounded reason.

Only a nonterminal, non-committing run can be cancelled. Cancellation preserves
the ledger and artifacts until explicit pruning.

## Plan and operation contracts

`WorkflowPlanV1` is canonicalized as UTF-8 JSON with sorted keys and compact
separators. Its SHA-256 hash is part of every approval and receipt.

The operation list is a Pydantic discriminated union keyed by `kind`. The
initial registry contains only existing, deterministic in-memory modifier
operations:

- `add_marker`
- `add_keyword`
- `trim_clip`
- `split_clip`
- `delete_clips`
- `reorder_clips`
- `add_transition`
- `change_speed`
- `assign_role`
- `batch_assign_roles`
- `batch_rename_clips`
- `fill_gaps`
- `fix_flash_frames`
- `batch_apply_transition`

Repeated `add_marker` operations replace a separate batch shape. Unsupported
operations fail plan validation before a run is created.

The server assigns stable sequence IDs (`op-001`, `op-002`, ...). Every
operation produces a typed receipt with:

- operation ID and kind;
- disposition;
- affected entity count and stable identities when available;
- before/after values when bounded;
- warnings;
- stable error code on failure.

The entire dry-run fails on the first failed operation. No destination changes
occur, but all completed operation receipts and the failed receipt are recorded.

## Preview contract

`WorkflowPreviewV1` contains:

- schema, graph, package, and run versions;
- run ID and state;
- source and destination paths;
- source SHA-256;
- prior destination state: absent or SHA-256;
- canonical plan SHA-256;
- candidate SHA-256 and size;
- semantic diff SHA-256;
- validation result and issues;
- ordered operation receipts;
- bounded summary and warnings;
- approval mode and expiration;
- run, event, and diff resource URIs.

Candidate XML is never embedded in the result.

## Graph nodes and deterministic gates

### 1. Inspect

- Resolve source and destination through `PathPolicy`.
- Reject same-file source/destination.
- Enforce source size.
- Hash source and any prior destination.
- Parse source through the safe XML boundary.
- Record an inventory sufficient for later semantic checks.

### 2. Normalize plan

- Validate the discriminated operation schema.
- Apply semantic preflight checks that need the source inventory.
- Assign operation IDs.
- Canonicalize and hash the plan.

### 3. Dry-run

- Create one isolated `FCPXMLModifier`.
- Apply the ordered operations in memory.
- Record each operation receipt.
- Never invoke a public MCP tool handler recursively.

### 4. Serialize and validate

- Serialize deterministic candidate bytes.
- Write them only to the private artifact directory.
- Validate the serialized artifact, not only the in-memory tree.
- Reparse it independently and check referential invariants.

### 5. Diff

- Compare source and candidate through the semantic FCPXML diff service.
- Persist a typed diff artifact.
- Render a bounded human summary.
- Hash the complete diff artifact.

### 6. Await approval

- Persist the complete preview projection and event.
- Return only after the run is durably `awaiting_approval`.

### 7. Commit

- Reconcile any prior interrupted attempt.
- Verify approval and expiration.
- Acquire the destination lock.
- Re-hash source, prior destination, plan, candidate, and diff.
- Persist `commit_started`.
- Perform the existing atomic replacement with validation and backup.
- Reopen and validate the destination independently.
- Verify the destination hash equals the candidate hash.
- Persist the final receipt and `committed`.

## State machine

```text
preparing
   |
   +------------------------------> failed
   |
   v
awaiting_approval
   |          |          |
   |          |          +-------> expired
   |          +------------------> rejected
   +-----------------------------> cancelled
   |
   v
approved
   |          |
   |          +------------------> stale
   v
committing
   |          |          |
   |          |          +-------> recovery_required
   |          +------------------> rolled_back
   v
committed
```

State transitions use compare-and-set semantics inside `BEGIN IMMEDIATE`
transactions. Terminal states never transition.

Stable state-related errors include:

- `approval_required`
- `approval_expired`
- `workflow_state_conflict`
- `workflow_stale`
- `operation_failed`
- `artifact_corrupt`
- `ledger_unavailable`
- `recovery_required`
- `idempotency_conflict`

## Approval

### CLI mode

`FCP_MCP_WORKFLOW_APPROVAL=cli` is the default.

`fcp-mcp workflow approve RUN_ID`:

1. verifies ledger and artifact integrity;
2. renders the plan, operations, validation, diff, paths, and hashes;
3. requires interactive confirmation when attached to a terminal;
4. records operator, host, terminal presence, timestamp, expiry, and binding
   hash;
5. atomically transitions `awaiting_approval` to `approved`.

Noninteractive approval requires both:

```text
--yes
--expect-candidate-sha SHA256
```

The command refuses redirected or noninteractive approval without both flags.

Approval binds:

- run ID;
- graph and plan schema versions;
- source and prior-destination hashes;
- canonical plan hash;
- candidate hash;
- complete diff hash;
- approval mode;
- expiration.

Approval is single-use and expires after 24 hours by default.
It is consumed only by the compare-and-set transition to `committing`; a lock
conflict or other failure before that transition leaves it available until
expiry.

### Client mode

`FCP_MCP_WORKFLOW_APPROVAL=client` is an explicit lower-friction opt-in.

The destructive commit call becomes the approval boundary. The server still
checks all hashes and records `approval_source=client`, but documentation and
receipts state that the server cannot prove the host showed a human approval
UI. Tool annotations remain hints rather than enforcement.

There is no disabled or automatic approval mode in v0.3.0.

## Ledger and artifacts

### State location

The implementation adds `platformdirs>=4.11,<5` as a direct runtime dependency.
`FCP_MCP_STATE_DIR` overrides the platform-specific `user_state_dir` returned by
`platformdirs`. On POSIX, the runtime creates directories with mode `0700` and
files with mode `0600`. On Windows it uses the per-user platform directory and
reports the effective permission posture through `fcp_doctor`. Every platform
rejects a state-root symlink and contained database, artifact, or lock paths
that resolve through symlinks or reparse points.

```text
state/
├── runs.sqlite3
├── artifacts/
│   └── RUN_ID/
│       ├── candidate.fcpxml
│       └── diff.json
└── locks/
    └── DESTINATION_SHA256.lock
```

Artifact paths are derived from server-generated IDs. No model input is used as
a relative artifact or lock path.

### Database tables

#### `schema_migrations`

- version
- migration name
- migration checksum
- package version
- applied timestamp

Migrations are forward-only. The database is backed up before a schema change.

#### `runs`

Materialized current state:

- run and graph identity;
- state and state revision;
- active profile and approval mode;
- source/destination paths and hashes;
- plan, candidate, diff, and receipt hashes;
- created, updated, approved, committed, and expiry timestamps;
- terminal error code and sanitized summary.

#### `events`

Append-only trajectory:

- run ID and monotonic per-run sequence;
- event type and canonical JSON payload;
- timestamp and elapsed duration when applicable;
- previous event hash and event hash.

Triggers reject update or deletion. The chain is tamper-evident, not
tamper-proof.

#### `artifacts`

Immutable artifact metadata:

- run ID and artifact kind;
- contained relative path;
- SHA-256 and byte size;
- creation timestamp.

Retention never deletes or updates these rows. Artifact availability after an
authorized prune is derived from append-only prune events, so a deliberately
removed body remains distinguishable from corruption.

#### `approvals`

Immutable approval/rejection records:

- run ID and decision;
- approval source;
- operator and host metadata;
- binding hash;
- created and expiry timestamps.

#### `idempotency_keys`

- caller key;
- canonical prepare-request hash;
- run ID.

Reusing a key with the same request returns the existing run. Reusing it with a
different request raises `idempotency_conflict`.

### SQLite configuration

Every connection uses:

```text
PRAGMA journal_mode=DELETE
PRAGMA synchronous=FULL
PRAGMA foreign_keys=ON
PRAGMA busy_timeout=5000
```

State-changing operations use explicit `BEGIN IMMEDIATE`. WAL is excluded
because the supported runtime matrix may include SQLite versions affected by
the documented WAL-reset bug and this workload does not need concurrent
writers.

Candidate XML and diff bodies remain outside SQLite. The ledger stores only
their metadata and hashes.

## Destination locking

A destination-scoped lock is acquired only during commit. Holding a lock across
human approval would create long-lived stale locks and is not permitted.

The lock filename is the SHA-256 of the resolved destination path. Creation uses
an atomic exclusive create and records:

- run ID;
- process ID;
- host;
- creation time;
- destination path hash.

Age alone never breaks a lock. Recovery checks process liveness, ledger state,
and destination/backup hashes. An ambiguous lock produces
`recovery_required`.

## Crash consistency and reconciliation

SQLite and the filesystem cannot share one atomic transaction. Commit therefore
uses an explicit intent protocol:

1. Acquire the destination lock.
2. Re-hash every approved precondition and artifact while holding the lock.
3. Generate a commit-attempt ID and a deterministic expected backup path.
4. Atomically consume the approval, persist `committing`, and append a
   `commit_started` event containing the attempt ID and expected backup metadata.
5. Execute the atomic file replacement using that attempt ID and backup path.
6. Reopen, validate, and hash the destination.
7. Persist the receipt and `committed`.
8. Release the lock.

No destination mutation begins before step 4 is durable. The atomic-write layer
must therefore accept the preassigned attempt ID and backup path rather than
creating recovery-critical identities after the intent record.

A crash after lock acquisition but before step 4 leaves an orphan lock on an
`approved` run. Explicit reconciliation may remove it only after proving the
recorded owner is no longer live and the source and destination preconditions
are unchanged; the approval remains unconsumed.

`fcpxml_workflow_status` inspects and reports the evidence without changing it.
`fcpxml_workflow_commit` and `fcp-mcp workflow reconcile` may persist a
reconciliation decision for a run left in `committing`:

- Destination equals the candidate hash:
  - validate the destination;
  - require the expected backup to match the approved prior hash when a prior
    destination existed;
  - reconstruct the receipt from the intent and artifact/backup evidence;
  - finalize `committed`.
- Destination equals the approved prior-destination hash or remains absent:
  - verify rollback evidence;
  - mark `rolled_back`;
  - require a new run for a deliberate retry.
- Destination matches neither:
  - mark `recovery_required`;
  - make no further project mutation.

No branch infers success from process exit, timestamps, or prose.

## MCP resources

Read-only bounded resources expose run evidence:

- `fcp-workflow://runs/{run_id}`
- `fcp-workflow://runs/{run_id}/events`
- `fcp-workflow://runs/{run_id}/diff`

Resource templates accept only a syntactically valid run ID. They do not accept
paths or queries. Candidate XML is not exposed as an MCP resource in v0.3.0.
These resources are registered in `workflow`, `edit`, and `full`; `inspect`
registers none of them.

## Observability

The ledger is the source of truth. Important transitions are mirrored to stderr
using the configured text or JSON log format.

Every workflow event includes:

- run ID and event sequence;
- graph, package, and schema versions;
- active profile and approval mode;
- node and attempt;
- start/end or elapsed timing;
- relevant hashes;
- disposition and stable error code.

Logs exclude:

- complete XML;
- marker values or notes;
- media content;
- complete operation payloads;
- approval operator details beyond what is necessary for local audit.

OpenTelemetry export is deferred. Field names should remain easy to map to
traces later, but v0.3.0 adds no telemetry runtime dependency.

## Meaningful structured outputs

Every existing tool retains its current successful text content while gaining a
concrete, validated structured result.

The MCP boundary uses a typed `CallToolResult` whose output annotation points to
a Pydantic model. The SDK therefore:

- publishes the concrete output schema;
- preserves explicit legacy `TextContent`;
- validates `structuredContent` before sending.

Common result concepts are:

- `schema_version`
- `summary`
- `warnings`
- typed artifact references

Tools add domain-specific fields:

- clip, marker, role, effect, timing, and validation records for FCPXML reads;
- affected entities and full transaction receipts for writes;
- stream, loudness, silence, beat, and scene records for media analysis;
- requested action and independently observed outcome for live operations.

Important fields may not use `Any`. Result contracts may share typed components,
but each tool must expose a schema appropriate to its actual promise.

Failures remain MCP tool errors with stable codes and no success payload.

All values use strict parsing and bounded ranges. Invalid configuration blocks

`fcp_doctor` adds:

- active profile and exact catalog;
- approval mode;
- state path and permission check;
- ledger schema and quick integrity check;
- SQLite runtime version and journal mode;
- incomplete/recovery-required run count.

## CLI

```text
fcp-mcp profiles [--json]
fcp-mcp serve [--profile PROFILE]
fcp-mcp workflow list [--state STATE] [--limit N] [--json]
fcp-mcp workflow show RUN_ID [--json]
fcp-mcp workflow approve RUN_ID [--yes --expect-candidate-sha SHA256]
fcp-mcp workflow reject RUN_ID [--reason TEXT]
fcp-mcp workflow verify [RUN_ID] [--json]
fcp-mcp workflow reconcile RUN_ID [--json]
fcp-mcp workflow prune --terminal --older-than DAYS [--yes]
```

`prune` never targets nonterminal or `recovery_required` runs and never deletes
ledger rows. For each eligible terminal run it appends a prune-intent event
containing the artifact paths and hashes, deletes only the candidate and diff
bodies, and then appends a completion event. An interrupted prune is resumable
from its intent. Run, event, artifact-metadata, approval, and receipt evidence is
retained. Verification reports an intentionally pruned body as `pruned`, not
`artifact_corrupt`.

## Evaluation strategy

The model never grades its own plan. Each graph edge has a deterministic gate:

- schemas and semantic preflight;
- safe parsing;
- source/destination hashes;
- operation receipts;
- serialized candidate validation;
- independent reparsing;
- semantic diff;
- approval binding;
- post-commit reopen, validation, and hash verification.

Tests grade both:

1. the trajectory: exact legal event/state sequence;
2. the outcome: actual destination, backup, candidate, receipt, and hashes.

### Required automated coverage

- Unit tests for every operation model and executor.
- Property-based tests for legal/illegal state-machine transitions.
- Property-based tests for operation parsing and canonical plan hashing.
- Golden candidate, diff, preview, event, and receipt fixtures.
- Path traversal, symlink escape, same-file, artifact containment, and lock-key
  tests.
- Approval binding, expiry, replay, rejection, cancellation, and client-mode
  tests.
- Idempotency-key reuse and conflict tests.
- Concurrent prepare and same-destination commit tests.
- Fault injection:
  - before lock acquisition;
  - after lock acquisition but before commit intent;
  - after commit intent;
  - after lock;
  - after backup;
  - before and after replacement;
  - after destination validation;
  - before final ledger commit;
  - during lock release.
- Reconciliation for candidate, prior-destination, missing, and ambiguous output.
- Ledger update/delete rejection, hash-chain tamper, artifact tamper, and SQLite
  integrity tests.
- Prune-intent recovery and deliberate-prune-versus-corruption tests.
- Profile-specific tool/prompt/resource catalogs.
- Meaningful output-schema and structured-result validation for all tools.
- Exact legacy text-content compatibility tests.
- Documentation tool-call validation against every active profile.
- Installed-wheel CLI, stdio initialization, resource, prepare, approve, commit,
  status, and recovery smoke.
- Python 3.10-3.13 and offline Windows coverage.

A real Final Cut Pro import of a committed canary is a separate,
maintainer-authorized release check.

## MCP SDK v2 migration gate

Workflow development remains on `mcp>=1.27,<2` until stable artifacts exist.

After the mandatory revalidation:

1. Update the dependency to the actual stable v2 range.
2. Replace `FastMCP` with `MCPServer`.
3. Move protocol imports from `mcp.types` to `mcp_types`.
4. Convert Python-side MCP fields to snake case.
5. Set `version=package_version()` through the public constructor.
6. Rebuild the domain-error boundary against v2's documented tool-error
   behavior.
7. Move direct protocol tests to the high-level `Client`.
8. Verify both 2025-era and 2026-07-28 negotiation over stdio.
9. Recheck Tasks but keep them deferred unless a new design is explicitly
   approved.

No v2 beta enters the production dependency range.

If stable v2 or the final protocol is delayed or materially changes, workflow
implementation may continue on v1, but publishing v0.3.0 requires an explicit
maintainer release decision.

## Compatibility and rollback

- All existing 89 tool names and accepted inputs remain available in `full`.
- `edit` retains every existing offline tool.
- Existing successful MCP text content remains exact unless a separate
  documented defect requires correction.
- Existing coded error behavior remains.
- `FCP_MCP_PROFILE=full` restores the complete catalog for existing clients.
- Version 0.2.1 ignores the v0.3 ledger and does not modify it.
- Reinstalling v0.3 resumes from its forward-compatible ledger schema.
- `fcpxml_apply_template` remains registered in `edit` and `full` but returns
  `unsupported_contract`.

- v0.3.0: transactional workflow graph, ledger, profiles, typed outputs, and

- v0.4.0: production recipes rebuilt on the transactional workflow surface.
- v0.5.0: proxy and offline-media awareness.

## Acceptance criteria

The release candidate is complete only when:

1. Every required automated test and existing Phase 0 gate passes.
2. Default stdio initialization exposes exactly the approved `workflow`
   profile.
3. `full` exposes every existing tool plus the four workflow tools.
4. Every successful public tool has a meaningful validated output schema and
   preserves its required text content.
5. Prepare never changes the destination.
6. CLI mode cannot commit without an unexpired, exact approval binding.
7. Every stale precondition fails without destination mutation.
8. Every injected crash reconciles to `committed`, `rolled_back`, or
   `recovery_required` from filesystem evidence.
9. No path, symlink, artifact, lock, or approval bypass survives adversarial
   tests.
10. The installed wheel passes CLI and MCP workflow smoke tests.
11. A fresh SDK/spec/SQLite research revalidation is recorded.
12. The design and implementation receive independent review.
13. No external push, tag, registry submission, or publication occurs without
    explicit authorization.
