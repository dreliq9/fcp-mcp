# fcp-mcp v0.3 Product Launch Design

**Status:** Approved for implementation and public release on 2026-08-09.

## Goal

Ship one coherent `fcp-mcp==0.3.0` product: a trusted, local, human-approved
FCPXML workflow system with optional Final Cut Pro handoff. The public package,
GitHub release, MCP Registry entry, repository metadata, documentation, sample
workflow, and verified executable must describe the same artifact.

## Product Decision

The launch includes the YouTube materialized-clip-plan adapter currently in
draft PR #2. The release therefore freezes the `v0.3.0` full profile at 94
tools, with `inspect=30`, `workflow=34`, `edit=75`, and `full=94`. The adapter
remains absent from the default read-oriented `workflow` profile and is exposed
only by the write-capable profiles.

The product promise is deliberately narrower than “autonomous Final Cut Pro.”
Apple defines FCPXML as an interchange format, not a complete representation of
native library state, and DTD validity does not prove successful or equivalent
import. fcp-mcp therefore promises bounded FCPXML inspection and editing,
reviewable transactions, provenance, and tested handoff into Final Cut Pro.
Live UI control remains optional and capability-limited.

## Approaches Considered

### A. Integrated v0.3 launch — selected

Merge the clip-plan handoff and product-polish work together, freeze the
94-tool surface, verify one artifact, and publish it as `v0.3.0` everywhere.
This avoids releasing an immediately obsolete 93-tool package and gives the
launch one demonstrable end-to-end workflow.

### B. Transactional v0.3 followed by handoff v0.3.1

Release current `main` first, then merge draft PR #2 and publish a patch. This
reduces the first release diff but creates two releases, two documentation
states, and a short-lived public catalog. It was rejected because v0.3 is not
yet published and PR #2 is already clean and fully green.

### C. Rebrand before release

Build a site, graphical installer, or desktop wrapper before publishing. This
would increase schedule and maintenance cost without improving the core FCPXML
contract. It was rejected; the MCP client is the UI for this release.

## Deliverables

### 1. One release identity

- Keep package, server manifest, CLI, wire server identity, changelog, and docs
  at `0.3.0`.
- Replace every stale 93-tool or 74-tool claim with the frozen 94/75 catalog.
- Remove release-candidate installation instructions once the tagged package is
  publicly available.
- Build one wheel and one source distribution from the exact release commit.
  The tag-triggered workflow must rebuild and verify rather than upload a local
  artifact.
- Publish in order: merged commit, signed or annotated `v0.3.0` tag, PyPI,
  GitHub Release, then MCP Registry. Record each public URL and version.

### 2. Outcome-led repository surface

The README first screen must answer four questions without scrolling through a
catalog:

1. What does fcp-mcp produce?
2. Which work is safe by default?
3. What is the fastest verified workflow?
4. What can Final Cut Pro’s public surface not guarantee?

Lead with the transactional clip-plan/FCPXML story rather than “most capable”
or raw tool count. Retain the detailed catalog as reference material after the
quickstart. Add repository topics and a homepage/docs target. Package metadata
must name a human maintainer; AI collaboration may be acknowledged in the
repository but is not a support identity.

### 3. Reproducible first run

Provide one golden path that requires no private media:

1. `pipx install fcp-mcp`
2. `fcp-mcp doctor`
3. configure one supported MCP client with the default `workflow` profile
4. inspect and transactionally modify the bundled sample FCPXML
5. verify the semantic diff, candidate hash, commit receipt, and output
6. optionally import the result into a disposable Final Cut Pro library

The checked-in sample must be redistributable, deterministic, and small. The
documentation must show exact expected output fields, not only tool names. The
release also includes a real-FCP visual proof captured from the release canary:
at minimum a screenshot of the imported timeline and a concise caption tying
it to the verified FCPXML artifact. No fabricated Final Cut Pro UI is allowed.

The YouTube handoff is the flagship advanced path. Its guide must state the
ownership boundary: YouTube MCP acquires and materializes evidence; fcp-mcp
authorizes local paths, verifies hashes, generates FCPXML and provenance, and
performs optional Final Cut Pro handoff.

### 4. Compatibility and support contract

Create a compatibility document covering:

- macOS floor and tested macOS release;
- tested Final Cut Pro release;
- accepted FCPXML versions and the DTD/import distinction;
- Python 3.10–3.13;
- tested MCP clients and exact installation commands;
- offline, workflow, edit, full, and live-control boundaries;
- required Accessibility and allowed-root permissions;
- unsupported template substitution, proxy relinking, generic native-library
  mutation, and unverified live UI behaviors.

Create a support document and issue templates for bug reports and feature
requests. Bug reports request package version, client, profile, `doctor --json`
output with private paths redacted, macOS/FCP versions, and reproducible steps.
The security policy and path/privacy behavior must be linked from the README.

### 5. Public proof and maintenance surfaces

- Preserve the detailed local release review, but add a concise public release
  evidence page with CI run, package hashes, profile counts, DTD result, live
  import result, and known residual risks.
- Enable GitHub Discussions only if a concrete support category and moderation
  owner are defined; otherwise Issues remain the support surface for v0.3.
- Add repository topics: `mcp`, `model-context-protocol`, `final-cut-pro`,
  `fcpxml`, `video-editing`, and `macos`.
- The repository homepage points to the canonical quickstart or documentation
  index, not an unimplemented marketing site.

## Release Architecture

The productization branch is based on draft PR #2 head
`095f71c2dfa9a8fc54de70e262201fb893e27fae`. It will be published as a new PR
that includes the draft handoff work and the launch polish. After that PR is
merged, draft PR #2 is closed as superseded with a link to the merged PR.

The release tag is created only from the verified merge commit. PyPI Trusted
Publishing uses the protected `pypi` GitHub environment and short-lived OIDC
credentials. MCP Registry submission uses the released PyPI `0.3.0` package;
the Registry manifest must never advertise an unpublished package version.

## Verification Gates

All gates apply to the isolated worktree and then to the installed release
artifact:

1. Complete pytest suite passes in an environment installed from this branch.
2. Ruff, documentation-call contracts, profile snapshots, result contracts,
   dependency audit, and trust-module coverage floors pass.
3. Wheel and source distribution pass `twine check` and inventory checks.
4. The wheel installs into a new temporary environment; CLI version, doctor,
   all four profiles, stdio initialization, the first-run workflow, and the
   YouTube handoff smoke pass from the installed wheel.
5. The release workstation validates the golden output against Final Cut Pro’s
   installed DTD and imports it into a disposable Final Cut Pro library without
   a warning. The resulting timeline is inspected and captured as real visual
   evidence.
6. PR CI is green at the exact reviewed head. After merge, the merge commit CI
   is green before tagging.
7. After publication, install `fcp-mcp==0.3.0` from public PyPI into a fresh
   environment and repeat version, doctor, stdio, profile, and first-run smoke.
8. Verify the GitHub Release and MCP Registry resolve to the same version and
   repository.

## Failure and Rollback Rules

- Before tagging, fix the branch and repeat every affected gate.
- A PyPI file or version is immutable. Never move or reuse `v0.3.0` after
  publication.
- If a published artifact is unusable or unsafe, stop Registry publication,
  mark the GitHub release, yank rather than delete the PyPI release when
  appropriate, and ship `0.3.1` from a new commit and tag.
- If Registry submission fails after PyPI succeeds, keep the verified PyPI and
  GitHub release, repair only the Registry metadata or publication path, and do
  not rebuild `0.3.0`.
- Draft PR #2 remains open until its commits exist on the merged launch branch.

## Out of Scope

- New tools beyond the clip-plan adapter already in draft PR #2
- Proxy/relink implementation, multicam, transcription, or media copying
- New live-control automation or claims beyond tested AppleScript/menu paths
- Desktop GUI, hosted service, accounts, telemetry, billing, or analytics
- A marketing website

Proxy and offline-media handling remains the first post-launch capability to
evaluate against real user feedback.

## Success Criteria

- A new user can install the public package, configure a supported client, run
  doctor, and complete the bundled transactional sample in under ten minutes.
- Package, CLI, manifest, documentation, PyPI, GitHub Release, and MCP Registry
  all report `0.3.0` and the same catalog counts.
- The public first-run artifact is linked to a real DTD and Final Cut Pro import
  result.
- The README makes the safety boundary and Apple limitation visible before any
  live-control setup.
- No unpublished, unsupported, or unverified capability is presented as
  working.
