# fcp-mcp v0.2.1 Trust Baseline Design

**Status:** Approved in design review on 2026-07-26
**Target release:** v0.2.1
**Base commit:** `a306424586955c1c5adc4a54ca7a196513ba10b1`
**Research record:** `docs/research/2026-07-26-phase-0-trust-boundary.md`

## Summary

Version 0.2.1 turns `fcp-mcp` from a broad but weakly guarded MCP server into
a trustworthy local execution plane. It preserves the public v0.2 tool names
and successful text responses while adding real diagnostics, deterministic
filesystem and live-control boundaries, atomic validated writes, accurate MCP
failure semantics, safe macOS automation arguments, contract tests, and a
reproducible release candidate.

This phase does not add agent graphs, durable memory, RAG, model routing, or
multi-agent orchestration. Those features cannot compensate for incorrect
tool contracts or unsafe mutations.

## Goals

1. Make every advertised success truthful.
2. Prevent path traversal, symlink escape, accidental source overwrite, and
   dynamic AppleScript/JXA source injection.
3. Make FCPXML mutations atomic, validated, recoverable, and observable.
4. Give users and agents one structured diagnostic surface.
5. Preserve v0.2 consumer compatibility wherever safety permits.
6. Make CI and built-package verification deterministic enough to gate a
   v0.2.1 release.
7. Record the primary-source research and decisions that govern the phase.

## Non-goals

- Migrating to MCP Python SDK v2 before it is stable.
- Reorganizing every tool into category modules.
- Converting all 88 existing success payloads to new structured schemas.
- Adding a generic workflow engine or knowledge graph.
- Implementing the undocumented template clip-replacement format.
- Publishing to PyPI, GitHub Releases, or MCP Registry without a separate
  user-authorized release action.

## Compatibility policy

- Keep every existing tool name.
- Keep every existing required input.
- Optional compatibility aliases may be added where published documentation
  used a different name.
- Keep existing successful text responses in v0.2.1.
- Convert known failure prose into MCP tool errors with stable codes.
- Safety defects are not compatibility promises: unrestricted paths,
  same-file writes, source interpolation, and false success are removed.
- Keep `fcp-mcp` with no arguments as the stdio server entry point.
- Pin the runtime SDK to `mcp>=1.27,<2`.
- Schedule the stable SDK v2 migration for v0.3.0 after a new research gate.

## Architecture

The existing `server.py` remains the MCP registration and compatibility
layer. New modules own deterministic policy and execution:

```text
fcp-mcp CLI / MCP stdio
          |
          v
   FastMCP registration
     |        |         |
     |        |         +--> macOS automation runner
     |        +------------> FCPXML transaction service
     +---------------------> read-only domain services
          |
          v
 configuration, path policy, diagnostics, contracts, structured audit events
```

### Module responsibilities

#### `src/fcp_mcp/cli.py`

- Parse `serve`, `doctor`, `doctor --json`, and `--version`.
- Start stdio when called with no arguments or `serve`.
- Print human diagnostics to stdout only when not serving MCP.
- Return documented integer exit codes.

#### `src/fcp_mcp/config.py`

- Build one immutable runtime configuration object.
- Parse and validate environment variables once.
- Expose package paths and capability flags to all services.
- Avoid module-level path policy derived independently in different modules.

#### `src/fcp_mcp/contracts.py`

- Define stable error codes and the `FCPMCPError` hierarchy.
- Define the structured doctor and transaction receipt models.
- Format v0.2-compatible success text separately from execution logic.

#### `src/fcp_mcp/security/paths.py`

- Resolve user paths using the configured roots.
- Enforce containment after symlink resolution.
- Distinguish readable inputs, generated outputs, and trusted internal system
  paths.
- Reject same-file input and output.

#### `src/fcp_mcp/automation/osascript.py`

- Execute constant AppleScript or JXA program text.
- Pass every dynamic value after the script so it arrives through `run argv`.
- Enforce timeout, return-code, stderr, and expected-result checks.
- Enforce the live-control capability gate before external actions.

#### `src/fcp_mcp/utils/atomic_write.py`

- Create secure temporary files in the destination directory.
- Flush and sync file content.
- Back up an existing destination.
- Atomically replace and sync the destination directory.
- Restore or clean up after a failed commit.

#### `src/fcp_mcp/fcpxml/transaction.py`

- Serialize modified XML through the generic atomic writer.
- Parse and validate temporary output before commit.
- Reparse and validate after commit.
- Produce an internal transaction receipt and structured audit event.

#### `src/fcp_mcp/diagnostics.py`

- Inspect package and SDK versions, server identity, catalog shape, runtime
  dependencies, configured roots, write access, live-control state, Final Cut
  Pro state, Accessibility readiness, FFmpeg/ffprobe, and Compressor.
- Never modify a project, launch an application, or trigger an export. The
  only permitted side effect is the temporary writeability probe described
  below.
- Return one `DoctorReport` model used by both CLI and MCP.

#### `src/fcp_mcp/server.py`

- Create the FastMCP v1 server with stable name `fcp-mcp` and versioned
  instructions.
- Register 89 tools and five prompts.
- Delegate policy and side effects to the modules above.
- Preserve public names, inputs, and successful text formatting.

## Configuration contract

### `FCP_MCP_OUTPUT_DIR`

The canonical directory for relative and generated outputs.

Precedence:

1. `FCP_MCP_OUTPUT_DIR`
2. Legacy `FCP_PROJECTS_DIR`
3. `~/Movies`

The directory is expanded and resolved. Doctor reports a failure if it does
not exist or cannot be written. Its writeability check may create and remove
one uniquely named empty probe file; it never changes project or media data.

### `FCP_MCP_ALLOWED_ROOTS`

An `os.pathsep`-separated list of roots that user-supplied paths may read.

- If set, every non-empty entry is expanded and resolved.
- If unset, the resolved output directory is the only allowed root.
- Relative input paths resolve beneath the output directory for compatibility.
- Absolute input paths are accepted only when their resolved targets remain
  beneath an allowed root.
- Symlink targets outside a root are rejected.

On macOS, multiple roots are configured as:

```text
FCP_MCP_ALLOWED_ROOTS=/Users/me/Movies:/Volumes/Media
```

### `FCP_MCP_ENABLE_LIVE_CONTROL`

- Default: disabled.
- Enabled values: `1`, `true`, `yes`, or `on`, case-insensitive.
- Required for FCP UI actions, live FCP queries that use Accessibility, opening
  libraries or XML in FCP, sharing, keyboard/menu dispatch, and Compressor.
- Not required for `fcp_is_running` or read-only discovery of installed local
  templates and share-destination names.

Doctor reports disabled live control as a warning rather than a broken offline
server. When live control is disabled, the Accessibility check is `skip` and
does not contact System Events. When enabled, doctor performs only a
non-mutating permission query.

## Path and write policy

### Read paths

- Must exist.
- Must resolve beneath an allowed root.
- Must be the expected file or directory kind for the tool.
- Extension checks are enforced where a tool has a defined format.

### Output paths

- Relative output paths resolve beneath `FCP_MCP_OUTPUT_DIR`.
- A generated output with no input must remain beneath
  `FCP_MCP_OUTPUT_DIR`.
- An omitted FCPXML output keeps the documented sibling
  `<input_stem>_modified.fcpxml` behavior.
- An explicit absolute FCPXML output must remain beneath either
  `FCP_MCP_OUTPUT_DIR` or the resolved input parent.
- Input and output resolving to the same file are always rejected in v0.2.1.
- An existing destination is backed up before replacement.

Known internal paths such as `/Applications`, Motion Templates, and FCP share
destinations are constructed by trusted code and are not accepted as arbitrary
user path roots.

## Transaction semantics

Every FCPXML mutation follows:

1. Resolve and validate input and output policy.
2. Parse the original.
3. Apply the in-memory transformation.
4. Reject a no-op when the operation promised a change.
5. Serialize to a secure temporary file beside the destination.
6. Flush and `fsync` the temporary file.
7. Parse and validate the temporary FCPXML.
8. Calculate input, temporary, and existing-destination SHA-256 hashes.
9. If the destination exists, create and sync a uniquely timestamped backup.
10. Commit with `os.replace`.
11. Sync the destination directory.
12. Reparse and revalidate the committed file.
13. On post-commit failure, restore the backup atomically or remove the new
    invalid destination when no previous destination existed.
14. Emit a final transaction event and return a receipt to the handler.

Validation errors abort before commit. Temporary files are removed on every
failed path. Validator warnings are recorded but do not block a structurally
valid file.

The built-in validator proves safe parsing and the structural invariants it
implements; it is not described as full Apple XSD validation. A disposable
Final Cut Pro import remains the authoritative pre-publication compatibility
check.

## Error contract

Expected domain failures raise `FCPMCPError` with a stable code:

- `invalid_arguments`
- `invalid_configuration`
- `invalid_path`
- `path_outside_scope`
- `source_not_found`
- `target_not_found`
- `same_file_forbidden`
- `live_control_disabled`
- `permission_denied`
- `dependency_missing`
- `command_failed`
- `output_missing`
- `validation_failed`
- `transaction_failed`
- `unsupported_contract`

The v1 FastMCP boundary converts these exceptions into tool results with
`isError: true`. Error text begins with the stable code and remains readable
by a model. Unexpected exceptions are logged with detail but return a
sanitized `internal_error` tool failure.

Successful v0.2 handlers retain their existing text formatting. The new
`fcp_doctor` tool returns a typed model and therefore supplies both
`structuredContent` and backward-compatible JSON text through FastMCP.

## Diagnostics contract

`DoctorReport` has:

```text
schema_version: "1"
status: "ready" | "degraded" | "blocked"
package_version: string
mcp_sdk_version: string
wire_server_version: string
protocol_target: "2025-11-25"
server_name: "fcp-mcp"
tool_count: integer
prompt_count: integer
checks: list[DoctorCheck]
```

Each `DoctorCheck` has:

```text
id: stable string
status: "pass" | "warn" | "fail" | "skip"
summary: string
details: object
remediation: string | null
```

CLI exit codes:

- `0`: ready
- `1`: degraded but offline MCP service remains usable
- `2`: blocked by invalid configuration or missing required runtime behavior

The doctor verifies an actual in-process catalog build. Installed-wheel smoke
tests separately verify real stdio initialization.

## macOS automation contract

- Script program text is a constant owned by the repository.
- Dynamic values are appended as process arguments and read by `on run argv`
  or the JXA equivalent.
- No helper accepts a fully assembled script containing user data.
- All calls use argument arrays with `shell=False`.
- Every call has a finite timeout.
- Nonzero status raises `command_failed`.
- Permission failures raise `permission_denied`.
- Live-control operations check `FCP_MCP_ENABLE_LIVE_CONTROL` before invoking
  `osascript`, `open`, or Compressor.

## Known contract repairs

### FCPXML versions

Versions are parsed as integer tuples. `1.11` is newer than `1.6`; it must not
produce the old-version warning.

### Cleanup prompt

The prompt must either request `fill_asset_ref` or omit the fill-gaps action.
It may not emit a schema-invalid tool call. The v0.2.1 prompt requests the
required asset reference explicitly.

### Workflow and guide examples

Every explicit tool call in `WORKFLOWS.md`, `LLM_GUIDE.md`, and registered
prompts is checked against the runtime input schema. Invalid argument names
are corrected. Claims unsupported by the implementation are removed.

### Template application

`fcpxml_apply_template` remains registered for compatibility but raises
`unsupported_contract`. Its documentation states that replacement is
unavailable until v0.3.0 defines a clip model and placeholder identity rules.
It must never claim that clips were applied.

### Media and external commands

FFmpeg/ffprobe discovery verifies a zero return code. Output-producing calls
also verify that the expected file exists and is nonempty before returning
success.

### Server identity

The documented FastMCP v1 API cannot set `serverInfo.version`; its low-level
server falls back to the installed MCP SDK version. Version 0.2.1 does not
mutate FastMCP's private `_mcp_server` attribute. Instead:

- MCP initialization keeps the stable server name `fcp-mcp`.
- Instructions identify `fcp-mcp v0.2.1` and the runtime-tested catalog of 89
  tools across 12 categories and five prompts.
- CLI and doctor report package version and wire/SDK version separately.
- Release notes disclose the v1 limitation.
- Phase 1 re-evaluates correct wire identity through the public SDK v2 API.

## Tool annotations

Every tool is explicitly classified:

- Offline inspection: read-only, non-destructive, closed-world.
- Offline file creation or modification: mutating; destructive only when an
  existing destination can change; closed-world.
- Media analysis: read-only when it creates no file; output-producing tools
  are mutating and closed-world.
- FCP/Compressor automation: mutating, potentially destructive,
  non-idempotent, open-world.

Annotations are verified from `tools/list`. They never replace path,
transaction, or live-control enforcement.

## Observability

All diagnostic and transaction events go to stderr so stdio JSON-RPC on stdout
cannot be corrupted.

Mutation events include:

- UTC timestamp
- event and operation name
- transaction UUID
- package version
- input and output paths
- input, output, and prior-destination SHA-256 hashes
- backup path when present
- validation outcome
- elapsed milliseconds
- final disposition: committed, rolled_back, or failed
- stable error code when failed

The default format is concise text. `FCP_MCP_LOG_FORMAT=json` selects one JSON
object per stderr line. Durable multi-node run ledgers remain a v0.3.0 feature.

## Test strategy

All behavior changes use red-green-refactor test-driven development.

### Unit tests

- Configuration precedence and boolean parsing.
- Root containment, traversal, symlink escape, relative resolution, extension
  checks, and same-file rejection.
- Atomic creation, backup, replacement, cleanup, and rollback.
- FCPXML pre- and post-commit validation.
- Version tuple comparison for 1.6, 1.9, 1.10, and 1.11.
- Constant automation source and hostile `argv` payloads.
- Subprocess nonzero status, timeout, and missing output.
- Doctor status aggregation and stable JSON schema.

### MCP contract tests

- Real initialization reports name and package version.
- Runtime catalog contains 89 unique tools and five prompts.
- Every tool has valid input/output schemas and annotations.
- Representative domain errors return `isError: true`.
- `fcp_doctor` returns schema-conforming structured content.
- Prompt-generated calls validate against live tool schemas.
- Documentation examples validate against live tool schemas.

### Integration and package tests

- Existing 119 tests remain green.
- Python 3.10, 3.11, 3.12, and 3.13 pass in CI.
- Overall coverage reaches 60%; every new module reaches 90%.
- Ruff 0.16.0 reports no violations.
- Build and `twine check` pass.
- A clean environment installs the wheel and verifies `--version`, doctor,
  stdio initialization, tool count, prompt count, and one offline tool call.
- Dependency audit reports no known vulnerabilities.

Live FCP mutation is not performed in CI. Before publication, a separate
manual gate exercises at least one read-only live query and one reversible
operation on a disposable project when Final Cut Pro and Accessibility
permission are available.

## CI and release behavior

CI must run tests, coverage, Ruff, contract/doc validation, build,
`twine check`, wheel installation, and dependency audit before publication can
start.

The publish workflow must consume the already verified artifact or repeat the
same gates before upload. Repairing and proving PyPI authentication,
attestations, MCP Registry publication, branch protection, and release
environment policy is Phase 2 work. No publication is part of this design's
implementation authorization.

## Risks and mitigations

### Existing users keep media outside `~/Movies`

Secure path defaults can reject a path that v0.2.0 accepted. Doctor, README,
and the error remediation show the exact `FCP_MCP_ALLOWED_ROOTS` setting for
external volumes. The release notes classify this as an intentional security
change.

### Central transactions touch many mutation tools

Characterization tests freeze existing successful output strings before a
handler is migrated. The shared writer is introduced behind those tests, and
each mutation family moves through it in a separate red-green cycle.

### SDK metadata support differs across v1 releases

Implementation may use only documented public SDK v1 APIs. If package version
identity or annotations cannot be expressed through those APIs, implementation
stops for a research revalidation rather than depending on private attributes.
The initial revalidation confirmed annotations are public and wire-version
configuration is not; the documented identity exception above is therefore
part of the v0.2.1 acceptance baseline.

### Backups can consume storage

Each replacement creates at most one uniquely named backup and reports its
path. Automatic backup pruning is excluded from v0.2.1 because deleting user
recovery data requires a separately designed retention policy.

### Structural validation is not Final Cut Pro

Tests use golden and adversarial FCPXML fixtures, but release readiness still
requires the documented disposable-project import gate. Claims in README and
LLM guidance are limited to checks the code actually performs.

## Phase completion criteria

Phase 0 is complete only when:

1. The original 119 tests and all new tests pass.
2. The quality, coverage, contract, security, package, and dependency gates
   above pass.
3. Every reproduced P0 audit finding is fixed, converted into a truthful
   explicit unsupported error, or covered by the documented FastMCP v1
   wire-version exception.
4. No tracked tool name or required input is removed.
5. The normal local `main` checkout remains unchanged.
6. The release candidate is committed on the isolated feature branch.
7. A fresh Phase 0 research revalidation finds no material change that
   invalidates the SDK or protocol decision.

## Follow-on phases

### Phase 1: v0.3.0 transactional workflow graph

Begin with fresh research of the stable MCP SDK v2 and 2026-07-28
specification. Migrate intentionally, introduce capability profiles, typed
outputs, a deterministic inspect-plan-dry-run-validate-diff-approve-commit
graph, and a durable run ledger.

### Phase 2: production release and governance

Research current PyPI trusted publishing, attestations, MCP Registry
publication, GitHub rulesets, dependency scanning, code scanning, canary, and
rollback guidance before implementation.

### Phase 3: project graph, only if justified

Measure retrieval and cross-session coordination needs. Add a provenance-rich
FCP project/asset graph only if simpler resources and run ledgers cannot meet
the measured use case.
