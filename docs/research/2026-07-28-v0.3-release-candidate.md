# v0.3 Release-Candidate Research Refresh

Date: 2026-07-28

## Scope

This research gate covers only Task 22: packaging and installed-artifact
evidence for the already-implemented transactional workflow release. It does
not add another orchestration layer or publish any artifact.

## Current upstream findings

### MCP Registry

- The current official Registry release is v1.8.0 (2026-07-13).
- The current `server.json` schema URI used by Registry examples is
  `https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json`.
- PyPI entries use `registryType: pypi`, `registryBaseUrl:
  https://pypi.org`, the distribution identifier, a matching package version,
  and `transport.type: stdio`.
- GitHub namespace ownership and PyPI package ownership are separately
  authenticated by the Registry. The repository already carries the required
  README marker `mcp-name: io.github.dreliq9/fcp-mcp`.

Sources:

- https://github.com/modelcontextprotocol/registry/releases/tag/v1.8.0
- https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/server-json/generic-server-json.md
- https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/server-json/official-registry-requirements.md

### Python packaging

- PyPA continues to recommend Trusted Publishing for automated PyPI uploads.
- The release artifact should be built as both an sdist and wheel, checked with
  `twine check`, then installed and exercised in an isolated environment.
- The existing publish workflow already separates verification from the
  Trusted Publishing job. Task 22 should update artifact names and installed
  smoke behavior without changing or triggering that publishing authority.

Sources:

- https://packaging.python.org/en/latest/guides/tool-recommendations/
- https://packaging.python.org/en/latest/flow/
- https://packaging.python.org/en/latest/guides/making-a-pypi-friendly-readme/

### Supported Python floor

The project advertises Python 3.10. A clean Python 3.10 import of
`fcp_mcp.workflow.locking` currently fails because `Self` is imported from
`typing`; `Self` entered the standard library in Python 3.11. The project
already depends on `typing_extensions`, so the compatible fix is to import
`Self` from there and prove it from an installed wheel on Python 3.10.

## Task 22 decision

The release gate will:

1. set package and Registry metadata to 0.3.0;
2. document the shipped workflow contract and stable MCP v2 boundary;
3. exercise the default and explicit profiles through installed stdio;
4. exercise representative legacy dual output;
5. prepare and commit a two-operation workflow using the reviewed candidate
   hash, proving prepare leaves the destination untouched;
6. read the run, event, and diff resources and verify hashes;
7. run installed CLI reconciliation on that real completed run as a no-op;
8. run doctor and inspect durable workflow diagnostics;
9. prove the wheel imports and runs on the advertised Python 3.10 floor; and
10. update CI and publish artifact names without triggering publication.

It will not add synthetic private-ledger fixtures to the installed smoke or
expand arbitrary per-module coverage floors. Those do not improve the public
evidence that an AI client can safely pilot Final Cut Pro workflows.
