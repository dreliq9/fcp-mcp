## Scope

This review evaluates the complete `origin/main...43e901e` branch diff against:

- [MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)

## Security and recovery findings

No unresolved security or recovery defect was found.

- Client approval requires the exact candidate SHA-256 and is created only
  inside the same compare-and-set transaction that persists commit intent.
- CLI approval is immutable, expiry-bound, terminal-aware, and cannot be
  substituted for client approval.
- Source, prior destination, plan, candidate, and diff evidence are rechecked
  while holding the destination lock before any destination mutation.
- State, database, artifact, snapshot, backup, and lock paths use private
  modes, no-follow descriptor traversal, server-derived names, and identity
  revalidation.
- Prepare never opens the destination for writing.
- Event rows are append-only and hash-chained; integrity verification checks
  sequence, hashes, canonical payloads, projections, approvals, artifacts, and
  commit evidence.
- Recovery never infers success from process exit, timestamps, or prose.
  Ambiguous destination, backup, lock, receipt, or artifact evidence resolves
  to `recovery_required`.
- The workflow core has no MCP SDK dependency and no generic graph, task,
  background-worker, or model-execution path.
- Live control remains independently opt-in and live action results preserve
  their explicitly unverified outcome strength.

## Contract and compatibility findings

No unresolved contract or compatibility defect was found.

- The default catalog is the exact 34-tool workflow profile.
- The full profile retains the 89 legacy tools and adds the four workflow
  tools.
- Prompt registration is profile-aware and every emitted tool call is checked
  against the active catalog.
- All public successes expose validated domain-specific structured content.
- Exact legacy text behavior is covered by frozen catalog and result-contract

- Candidate XML remains private; only run, event, and bounded diff resources

- Operational entry points reject non-macOS platforms before configuration,
  state, SQLite, catalog, subprocess, or filesystem side effects.
- The Ubuntu publisher is artifact-only and cannot install, import, test, or
  execute `fcp-mcp`.

## Resolutions

The first coverage run found `src/fcp_mcp/utils/atomic_write.py` at 86.18%,
below the existing 90% trust-module floor. The floor was not weakened.

Commit `f664f0e` added one focused regression proving that a short backup write:

- raises a coded transaction failure;
- removes the partial backup;
- preserves the prior destination; and
- leaves no temporary output.

The focused module coverage rose to 91%, and the complete coverage gate then
passed with all 11 trust modules above the required floor.

The workstation did not have `actionlint` installed. Version 1.7.12 was
downloaded to a temporary directory from the official release, verified
against the release checksum
`aba9ced2dee8d27fecca3dc7feb1a7f9a52caefa1eb46f3271ea66b6e0e6953f`,
and run without modifying project dependencies or the system installation.

The Task 24 command examples were corrected to use the actual full-profile
contract invocation and a private canonical `/private/tmp` state directory.

Live testing after the initial review exposed two Apple-contract defects and
one live-read serialization defect. Commit `43e901e` resolved them without a
workflow-state migration:

- `asset-clip` role writes now use the DTD-valid `audioRole` attribute, while
  reading legacy `role` remains backward compatible;
- the installed-wheel smoke asset now contains its required `media-rep`;
- release workstations can run `scripts/apple_dtd_gate.py` against the DTD
  bundled with their installed Final Cut Pro; and
- project durations are serialized from Apple's rational time record rather
  than calling `toString()` on the record object.

## Residual risks

- Client-mediated approval is intentionally recorded as
  `client_unverified_human`; the server cannot prove that a host displayed a
  human approval UI.
- The local ledger is tamper-evident, not tamper-proof against a process with
  the same user authority.
- One deliberately concurrent local run of two complete suites produced one
  isolated candidate-validation failure. Five focused reruns and both required
  sequential complete-suite runs passed. CI runs test and coverage jobs on
  separate runners, so the stress setup does not match the release workflow,
  but the observation is retained here rather than discarded.
- All eight remote checks passed at pushed commit `026d3af`; the live-test
  correction commit `43e901e` still requires its post-push CI run.
